# SwiftUI semantic audit — August 2026

Every previous parity pass compared **names**. `Tools/APIParity/api_parity.py`
says whether a symbol exists and whether its argument labels match, and
`CompileCorpus.swift` says whether a call site binds. Neither can say whether
the thing it binds to *means what SwiftUI means*. This audit asked only that
question, across the whole API, against Apple's own words.

**The question, exactly:** would code written for SwiftUI compile under TUIkit
and do the same thing? Not "is TUIkit different" — a terminal counts cells
where SwiftUI counts points, and a deviation that is well-reasoned, necessary,
harmless to porting (an extra defaulted argument, a TUI-only modifier beside the
SwiftUI one) or justified in the docs is not a defect. What counts is source
that ports cleanly and then behaves differently, or that fails in a way its
author could not have predicted.

## What was compared, and against what

SwiftUI's own documentation, extracted locally rather than scraped: the macOS
26.3 SDK's symbol graphs carry Apple's full doc comments, so
`swift-symbolgraph-extract` over `SwiftUI` + `SwiftUICore` yields **8,063 public
declarations, 7,538 of them documented** — the authoritative per-symbol
semantics, offline and version-stamped. The same treatment of TUIkit gave 3,921
declarations, 3,597 documented (a number that exists because `missing_docs` is
enforced). Both corpora were reduced to one markdown file per owning type so
the two could be read side by side.

Sixteen API families were then audited in parallel — layout stacks, layout
modifiers, geometry and the `Layout` protocol, text, text input, buttons and
menus, value controls, `List`/`ForEach`, `Table`, scrolling, navigation and
presentation, state and data flow, animation, colour and styling, input and
gestures, and app/scene structure. Each family got an analyst that read both
frameworks and the implementation, and then an adversarial verifier whose brief
was to **refute** the analyst, defaulting to refuted where the evidence did not
hold. Several verifiers went further than reading: they built throwaway probe
packages linking this repo by path and *measured* the rendered buffers, which
is why the findings below quote output rather than describe it.

**155 findings; 119 confirmed, 26 confirmed with a correction, 6 refuted, 4
unverified. The verifiers added 24 more that the analysts had missed.**

## Before the audit could start: two tooling defects

`api_parity.py` dropped any symbol unconditionally unavailable on **any**
platform. `Slider`, `Stepper`, `Table` and `Gauge` are all unavailable on
*tvOS* and all perfectly ordinary macOS API, so the rule deleted them — and
every member they own — from SwiftUI's side of the comparison. It was not
symmetric either: TUIkit annotates no platform unavailability at all, so the
rule only ever subtracted from SwiftUI, turning real gaps into silence.

**2,177 live macOS symbols were invisible, 180 of them `View` modifiers** —
including the whole of `KeyPress` and `View.onKeyPress`, `KeyboardShortcut`'s
own members, `Table`'s initializers, `View.onExitCommand`, `onMoveCommand` and
`EnvironmentValues.resetFocus`. Keyboard and table surface, which is to say the
parts of SwiftUI a terminal framework is most likely to want and least able to
notice missing. Fixed in `7e0edd53`; SwiftUI's counted surface went 5,181 →
6,759, and thirteen new family rules in `parity-map.json` account for the
clusters a character grid genuinely cannot express (AppKit bridging, GPU
shading, visionOS, Pencil, the Touch Bar, windows, the document architecture,
pointer styling, Writing Tools, the macOS 26 drag-session API, menu-bar
commands, WidgetKit, the share sheet). `--stale` rejected eleven speculative
patterns that matched nothing; they were removed rather than left as decoration.

The second defect was mine, in the corpus builder, and had the same shape —
worth recording because the two were written independently three years apart
and both reached for "unavailable anywhere means gone".

## Root causes worth deciding once

Several findings below are the same defect wearing different clothes. Fixing
the mechanism closes the cluster; fixing the symptoms does not.

**1. Metadata does not survive a wrapper view.** `.zIndex(1).padding(0)`
silently loses its place in the draw order, because `_ZIndexView` is found by a
static witness that every wrapping view type answers `false` for. The same hole
swallows alignment guides and layout values. I wrote the `ModifiedView` half of
the fix and then **reverted it**: it is three lines and strictly more correct,
but ~40 single-content wrapper types would each need the same forwarding, and a
half-fix makes the current honest rule ("apply it as the outermost modifier")
false-but-mostly-true, which is harder to reason about than the limitation. The
full fix is cheap at runtime — `static var _providesZIndex: Bool { Content._providesZIndex }`
is a compile-time constant chain — but it is a decision about a hot path, and
about whether every future wrapper must remember. **Recommendation:** adopt a
`MetadataForwarding` protocol with a default implementation, conform every
single-content wrapper, and add a test that fails when a new wrapper forgets.

**2. A modifier makes a view opaque to child resolution.** `resolveChildViews`
unwraps `ChildViewProvider`s, and `ModifiedView` is not one — so
`Group { A; B }.foregroundStyle(.red)` inside an `HStack` **rotates the layout
90°**, and a modified `GridRow` stops being a row and corrupts the grid's
column lattice for every other row. SwiftUI's rule is explicit for both types:
the modifier applies to each member, not to the group. The `ForEach` half of
this is fixed (`38b07ced`); the axis is not. **Recommendation:** conform
`ModifiedView` to `ChildViewProvider` when its content is one, re-wrapping each
resolved child in the same modifier. Note the one exception to get right:
`onDelete`/`onMove` are declared on `DynamicViewContent`, not `View`, and must
keep applying to the collection.

**3. `\.isEnabled` has no readers in the big containers — FIXED (`291b8754`), kept here for the shape.** `List`, `_ListCore`,
`Table` and `ScrollView` never consult it, and each type's concrete
`disabled(_:) -> Self` overload wins overload resolution over the `View`
extension — so `List { … }.disabled(true)` never even builds a
`DisabledModifier`. An ancestor's `.disabled(true)` therefore leaves the three
biggest containers fully interactive, and a `Button` inside a disabled `List`
still fires. **Recommendation:** have each core compute
`self.isDisabled || !context.environment.isEnabled`, as `Button` already does,
and publish `\.isEnabled = false` into the content it renders.

**4. The Optional third state, for the fourth and fifth time.** `Font??`,
`UnitPoint??` and `Transaction?` were each needed so "nobody said" and "said
none" stay distinguishable. `textCase` was the same and is now fixed; the
remaining instances are in the findings below. Worth a note in the contributing
guide: **any environment value whose SwiftUI type is itself Optional needs two
levels here.**

**5. A protocol conformance is the seam.** `PickerOptionProvider`,
`ButtonProvider`, `SectionRowExtractor`, `GridRowProviding` and
`ListRowExtractor` all mean "the container reflects over its content by asking
each child type". Every one of them has a case where the child is a type nobody
conformed — a `Section` in a menu, a `TupleView` of two `Section`s in a `List`,
a modified `GridRow` — and in every case the content silently disappears or is
mis-classified rather than failing. **Recommendation:** these should share one
fallback rule, and it should be loud in debug rather than empty.

## How to read the list

Ordered by severity, then by family. Severity means:

- **silent divergence** — it compiles, it runs, it means something else. The
  worst case, and the one both governing rules exist to prevent.
- **compile-break** — SwiftUI source binds to nothing. Rule 2's *correct*
  failure mode, so these are listed as work, not as bugs.
- **missing** — absent, and a character grid could carry it.
- **doc drift** — the behaviour may be right; the documentation is not.

Each entry quotes the SwiftUI sentence that establishes the promise, names the
file and line that decides TUIkit's behaviour, gives a concrete divergence
someone can turn into a failing test, and ends with a recommendation. Where the
verifier corrected the analyst, both are shown.

### Table

**1. `Table.init(_:selection:columns:) with Binding<Value.ID?>`**

- *SwiftUI:* swiftui-docs/Table.md, "Supporting selection in tables": "Binding to a single instance of the table data's id type creates a single-selection table." Apple's prose stops there — it does not state the click rule — so the SwiftUI side rests on the macOS/NSTableView convention it inherits, where a plain click always selects the row it lands on and never deselects (deselection being Command-click's job). That unquotability is why this is medium rather than high confidence.
- *TUIkit:* Sources/TUIkit/Focus/ItemListHandler+Selection.swift:151-160 — `func handleClickSelection(at index: Int, event: MouseEvent) { … guard selectionMode == .multi else { toggleSelectionAtFocusedIndex(); return } …` — and toggleSelectionAtFocusedIndex at :181-192: `case .single: if singleSelection?.wrappedValue == itemID { singleSelection?.wrappedValue = nil } else { singleSelection?.wrappedValue = itemID }`. Table routes its row clicks straight there (Table.swift:2739, `captureHandler.handleClickSelection(at: index, event: event)`); _ListCore.swift:2141 is the twin. Note the asymmetry: in multi mode a plain click is macOS-correct (`multiSelection?.wrappedValue = [clickedID]`, :176) — only single-selection toggles. — `Sources/TUIkit/Focus/ItemListHandler+Selection.swift:188`
- *Divergence:* `Table(people, selection: $selected)`; click "Mei", then click "Mei" again. SwiftUI leaves `selected == mei.id` both times; TUIkit leaves `selected == nil` after the second click. A detail pane driven by `if let selected { … }` blanks itself on a second click the SwiftUI author expects to be a no-op — and with .onRowActivate a second click is a routine part of an open gesture. This IS pinned deliberately: Tests/TUIkitTests/MultiSelectionClickTests.swift:189-204, @Test("Single-selection mode keeps its click-to-toggle behaviour"), asserts `box.selection == nil` with the comment "clicking the selected row again deselects (existing behaviour)"; ItemListHandlerTests.swift:250 pins the keyboard half. So it is a conscious choice — though the test's own wording reads as inherited rather than chosen for parity.
- *Recommendation:* Decide and document rather than keep both silently. Keep the Space-key toggle — it is a good terminal affordance — but the mouse path is the one that departs from the platform TUIkit imitates; the fix is one branch in handleClickSelection's single-selection case (assign `singleSelection?.wrappedValue = itemID` unconditionally, leaving toggleSelectionAtFocusedIndex to the keyboard). If it stays, record it in SwiftUI-compatibility.md section 2 — a selection binding going nil under the user's finger is exactly what a port discovers in production.

**2. `View.disabled(_:)`**

- *Status:* **FIXED** (291b8754): `Table`, `_ListCore` and `ScrollView` read `isDisabled || !context.environment.isEnabled`.

- *SwiftUI:* swiftui-docs/View.md, View.disabled(_:): "Adds a condition that controls whether users can interact with this view. The higher views in a view hierarchy can override the value you set on this view. In the following example, the button isn't interactive because the outer `disabled(_:)` modifier overrides the inner one" — followed by `HStack { Button(Text("Press")) {}.disabled(false) }.disabled(true)`. TUIkit's own DisabledModifier.swift:33-50 implements that cascade (`let enabled = context.environment.isEnabled && !disabled`) and documents that "controls combine it with their own disabled state".
- *TUIkit:* `grep -n 'isEnabled' Sources/TUIkit/Views/Table.swift` returns no matches. The only gates are the view's own stored flag: Table.swift:1053 `ItemListHandler(… canBeFocused: !isDisabled)`, :1069 and :1691 `handler.canBeFocused = !isDisabled`, and :2403 `guard !isDisabled, !context.isMeasuring, let mouseDispatcher = context.environment.mouseEventDispatcher else { return }` — the sole gate on all mouse wiring, header-sort handlers included. `isDisabled` is written only by the member `Table.disabled(_:)` at :370-374 (`copy.isDisabled = disabled`). Every other control in the framework does combine the two — Button.swift:325, TextField.swift:358, _ToggleCore.swift:420, Slider.swift:422, Stepper.swift:434, RadioButton.swift:297/554, DatePicker.swift:291, SecureField.swift:302, TextEditor.swift:139, _PickerMenuCore.swift (x5) all read `self.isDisabled || !context.environment.isEnabled`. … — `Sources/TUIkit/Views/Table.swift:2403`
- *Divergence:* `VStack { Table(people, selection: $selected) { TableColumn("Name", value: \.name) } }.disabled(isLoading)`. In SwiftUI the table is inert and greyed while loading. In TUIkit it still takes Tab focus, still moves its row cursor on Up/Down, still selects on Space or click (writing $selected), still sorts on a header click, and is not dimmed. Conversely the escape hatch SwiftUI explicitly rules out — an inner `.disabled(false)` — does re-enable here, because Table.disabled(false) just clears the local flag. Failing test: render `VStack { Table(…) }.disabled(true)` and assert `buffer.hitTestRegions.isEmpty` and `focusManager.currentFocused == nil` — the mirror of TableRenderTests.disabledNoHitRegion, which only ever applies .disabled() to the Table itself. No test covers the ancestor case; ModifierPropagationTests covers Button/Toggle/RadioButtonGroup but never a List or Table.
- *Recommendation:* Fix. One line in each of _TableCore.renderToBuffer and _ListCore.renderToBuffer: `let isDisabled = self.isDisabled || !context.environment.isEnabled`, used for canBeFocused and for the attachMouseHandlers guard — exactly the idiom the other eleven controls already use.

### Animation

**3. `Animation.default`** · *adjusted on verification*

- *SwiftUI:* swiftui-docs/Animation.md, `## Animation.default`: "The `default` animation is ``spring(response:dampingFraction:blendDuration:)`` with: `response` equal to `0.55`, `dampingFraction` equal to `1.0`, `blendDuration` equal to `0.0`. Prior to iOS 17, macOS 14, tvOS 17, and watchOS 10, the `default` animation is ``easeInOut``." It is also the default argument of withAnimation (swiftui-docs/withAnimation______.md).
- *TUIkit:* `public static let \`default\` = Animation.easeInOut`, with `public static let defaultDuration: TimeInterval = 0.35` at line 82. So `.default` is easeInOut(duration: 0.35) — SwiftUI's pre-iOS-17 definition. No test pins `.default`; AnimationTimingTests only asserts `Animation.easeInOut == Animation.easeInOut(duration: Animation.defaultDuration)`. — `Sources/TUIkitCore/Animation/Animation.swift:86`
- *Divergence:* `Animation.default.totalDuration == 0.35` in TUIkit. SwiftUI's default is a critically damped spring with response 0.55, which at 0.35 s is only ~78% of the way to its target and approaches asymptotically rather than with easeInOut's symmetric deceleration. Every ported `withAnimation { … }` with no explicit animation therefore runs ~36% faster and with a different velocity profile. Test: `#expect(Animation.default == Animation.spring(duration: 0.55, bounce: 0))` fails today.
- *Verifier's correction:* TUIkit's `Animation.default` is `easeInOut(duration: 0.35)` and finishes at 0.35 s, while SwiftUI's is a critically damped spring that is 93% of the way at 0.35 s and settles at ~1.0 s. The faithful port is `Animation.spring(duration: 0.5, bounce: 0)` — a curve TUIkit already ships as `Animation.spring`/`Animation.smooth` — not `spring(duration: 0.55, bounce: 0)` (Apple's doc says response 0.55, but the shipped framework resolves `.default` to the 0.5 spring). Test it on the curve, e.g. `Animation.default.fraction(at: 0.35) ≈ 0.93` and `totalDuration ≈ 1.0`, never on `==`.
- *Recommendation:* Fix — it is one line. TUIkit's spring(duration:bounce:) already parameterises the spring exactly as SwiftUI's response/dampingFraction do (omega = 2π/duration, zeta = 1 − bounce), so `Animation.spring(duration: 0.55, bounce: 0)` is the faithful port. If the shorter ease is preferred for a terminal, record it in SwiftUI-compatibility.md §2 — the neighbouring doc comment on defaultDuration says "Matches SwiftUI's", which invites the reader to assume .default matches too.

**4. `Animation.delay(_:)`**

- *SwiftUI:* SwiftUI's Animation is a stack: `Animation.base` is `any CustomAnimation` (swiftui-docs/Animation.md, `## Animation.base`) and `Animation.init(_:)` wraps one, so each modifier wraps the receiver and a repeat repeats whatever it was applied to, delay included. The individual effects are documented — "Delays the start of the animation by the specified number of seconds" (Animation.delay(_:)), "Repeats the animation for a specific number of times" (Animation.repeatCount(_:autoreverses:)) — but the composition rule is not stated in any doc comment, which is why this is medium confidence and worth confirming against a real SwiftUI build.
- *TUIkit:* Animation is a flat record of (curve, passDuration, delayInterval, speedFactor, repeatMode) and each modifier writes one field while copying the rest: `delay(_:)` sets `delayInterval: delayInterval + delay` and preserves repeatMode; `repeatForever(_:)` sets repeatMode and preserves delayInterval. `fraction(at:)` (Animation.swift:280) subtracts `effectiveDelay` exactly once before counting passes, and `effectiveDelay` (line 243) is always `delayInterval / speedFactor`. So the delay is always a single leading delay, always scaled by the final speed, whatever order the modifiers were written in. — `Sources/TUIkitCore/Animation/Animation.swift:195`
- *Divergence:* (1) `Animation.linear(duration: 1).delay(0.5).repeatForever(autoreverses: false)` — SwiftUI repeats the delayed animation, giving a 1.5 s cycle with a 0.5 s pause before each pass; TUIkit gives one 0.5 s pause then a continuous 1 s cycle for ever (`fraction(at: 1.6) == 0.1`). This is the shape a breathing/staggered decoration is written in. (2) `Animation.linear(duration: 1).speed(2).delay(1)` — SwiftUI's delay sits outside the speed, so it is 1 s; TUIkit gives `effectiveDelay == 0.5`. AnimationTimingTests pins only the other order (`.delay(1).speed(2)` → 0.5, test "Speed scales the delay too"), which agrees in both frameworks, so the divergent order is untested.
- *Recommendation:* At minimum document it on delay(_:): the delay is a single leading delay, it does not repeat with the animation, and modifier order does not matter. A proper fix needs a Repeat mode that can carry a per-pass delay — and must not disturb AnimationCycle.init?, which deliberately refuses to pre-render a delayed repeatForever for the opposite reason (Sources/TUIkitView/Animation/AnimationCycle.swift:75).

**5. `View.transition(_:)`**

- *SwiftUI:* A view inserted or removed inside withAnimation with no `.transition(_:)` fades — SwiftUI's default transition is `.opacity`. Note: I could NOT find a doc-comment sentence establishing this in the extracted SDK docs; swiftui-docs/View.md `## View.transition(_:)` says only "When this view appears or disappears, the transition will be applied to it", and neither AnyTransition.md nor Transition.md names the default. Hence medium confidence.
- *TUIkit:* `AnyTransition.identity` is documented as "Appears and disappears at once — the default, and what a view without `.transition(_:)` does", and the code agrees: only `_TransitionView` calls `storage.departures.present(…)`, so with no `.transition` nothing is recorded and Optional's `.none` branch renders `context.stateStorage?.departures.departing(…) ?? FrameBuffer()` — an empty buffer (Sources/TUIkitView/Core/PrimitiveTypes+View.swift:43-50). Insertion is symmetric: with no _TransitionView there is no arrival phase, so the view draws at full presence on frame one. — `Sources/TUIkit/Animation/AnyTransition.swift:75`
- *Divergence:* `if showDetail { Detail() }` (no .transition) with `Button("Toggle") { withAnimation { showDetail.toggle() } }`. SwiftUI cross-fades Detail in and out; TUIkit pops it in and out instantly. The ported source compiles and animates nothing, with no diagnostic.
- *Verifier's correction:* One overstatement to trim: it is not undocumented everywhere — AnyTransition.swift:75-76 states that `.identity` is "the default, and what a view without `.transition(_:)` does". That is a statement of behaviour, not a justification, and SwiftUI-compatibility.md still says the whole family is unimplemented, so the recommendation (record it in §2) stands.
- *Recommendation:* Document, don't fix. Defaulting to .opacity would mean wrapping every conditional child in a departure-recording view, costing a buffer copy plus a store write per conditional per frame in a framework that rebuilds the whole frame from the tree — a sound reason to decline. But it appears nowhere in SwiftUI-compatibility.md, so a porter discovers it by watching their app not animate. Add it to §2 (intentional divergence).

### App and scene structure

**6. `ContentUnavailableView.search / ContentUnavailableView.search(text:)`**

- *SwiftUI:* swiftui-docs/ContentUnavailableView.md, §ContentUnavailableView.search: "A `ContentUnavailableView` initialized with this static member is expected to be contained within a searchable view hierarchy. Such a configuration enables the search query to be parsed into the view's description."
- *TUIkit:* Sources/TUIkit/Views/ContentUnavailableView.swift:151-157 is a `static var` computed at construction: `label: { Text("No Results") }, description: { Text("Check the spelling or try a new search.") }`. It reads no environment, and there is nothing for it to read — SearchableModifier publishes only \.isSearching and \.dismissSearch to its content (Sources/TUIkit/Extensions/View+Searchable.swift:206-208), never the query string. Both strings are English literals; Text's literal init treats them as LocalizedStringKeys, which miss (framework keys are dot-separated) and fall back to themselves. — `Sources/TUIkit/Views/ContentUnavailableView.swift:151-157 (and :165-170 for search(text:))`
- *Divergence:* Inside `.searchable(text: $query)` with query == "zzz", SwiftUI's ContentUnavailableView.search renders a description naming the query; TUIkit renders "Check the spelling or try a new search." for every query, with no signal that the static is inert. Separately, after LocalizationService.shared.setLanguage(.french) the view still reads "No Results" — the same defect the project already fixed for Alert's presets (compat doc §4a: "they defaulted their titles to hardcoded English words, so a German app got a 'Warning' alert. They now default to the framework's own `label.warning`…"). ContentUnavailableViewTests.swift:62 and :72 pin the English literal, so a localization fix must update them; nothing pins the query omission.
- *Recommendation:* Fix both halves. Have SearchableModifier publish the query on an environment key beside \.isSearching and make .search a small view that reads it (.search(text:) stays as the escape hatch for a hand-rolled search bar, which is what SwiftUI's is for). Add contentUnavailable.noResults / .noResultsFor / .checkSpelling to Localization/translations/*.json and LocalizationKeys.swift.

**7. `EnvironmentValues.locale`** · *adjusted on verification*

- *SwiftUI:* swiftui-docs/EnvironmentValues.md:1423 — `var locale: Locale { get set }`, "The current locale that views should use." SwiftUI seeds it from the user's locale, region included.
- *TUIkit:* The key's default is correct (Sources/TUIkit/Environment/LocaleEnvironment.swift:19, `static let defaultValue = Locale.autoupdatingCurrent`), but the live environment is overwritten every frame at Sources/TUIkit/Environment/ServiceEnvironment.swift:234: `locale = LocalizationService.shared.currentLanguage.locale`, and that property is Sources/TUIkit/Localization/LocalizationService.swift:45-47 `public var locale: Locale { Locale(identifier: rawValue) }` where rawValue is one of the seven bare language codes en/de/fr/it/es/zh/ja. currentLanguage comes from systemPreferredLanguage() (LocalizationService.swift:242-251), which keeps only `langCode.prefix(2)` and maps anything outside the seven to .english. — `Sources/TUIkit/Environment/ServiceEnvironment.swift:234 (with Sources/TUIkit/Localization/LocalizationService.swift:45-47 and :242-251)`
- *Divergence:* On a machine whose locale is en_GB, SwiftUI's \.locale is en_GB (dates read 25/08/2026, week starts Monday); TUIkit's is Locale(identifier: "en"), giving US conventions. On a pt_BR machine — not one of the seven bundled languages — TUIkit falls back to .english so \.locale is "en" and a number formatted through the environment locale reads 1,234.5 where SwiftUI produces 1.234,5. Note the internal inconsistency too: \.calendar and \.timeZone keep autoupdatingCurrent (LocaleEnvironment.swift:24,:29) and are not re-derived, so a French-language app on a US machine gets fr formatting with the US calendar. Tests/TUIkitTests/LocaleEnvironmentTests.swift pins only the KEY default on a bare EnvironmentValues() and that an override reaches a subtree; it never exercises applyRuntimeServices, so the live value is unpinned.
- *Verifier's correction:* The residual divergence is the UNBUNDLED-LANGUAGE fallback only, not region loss generally. LocalizationService.init() (LocalizationService.swift:84-91) maps any system language outside {en,de,fr,it,es,zh,ja} to .english, so ServiceEnvironment.swift:234 publishes Locale(identifier: "en") on a pt_BR machine and a value formatted through the environment locale reads 1,234.5 where SwiftUI produces 1.234,5. The documented rationale ("the app's chosen language drives its formatting") does not cover this case — nobody chose English, the table simply does not exist. The en_GB region case is a documented, deliberate trade-off and is not a finding.
- *Recommendation:* Narrow the override: publish Locale.autoupdatingCurrent whenever its language code equals currentLanguage.rawValue (the common case — nobody has switched the app language away from the system's), and fall back to the bare code only when the app language was explicitly set to something else. That keeps the 'app language drives formatting' property the code comment at LocalizationService.swift:41-44 wants, without discarding a region the user did state.

**8. `Form / FormStyle.columns`**

- *SwiftUI:* swiftui-docs/FormStyle.md, §FormStyle.columns: "A non-scrolling form style with a trailing aligned column of labels next to a leading aligned column of values." swiftui-docs/Form.md adds that a form renders "as aligned vertical stacks on macOS". SwiftUI realises that column as a layout alignment, so it survives arbitrary view nesting.
- *TUIkit:* Sources/TUIkit/Views/Form.swift:188-206 recovers the row structure by scanning the content value's STATIC TYPE: `if let extractor = view as? FormContentExtractor { return extractor.extractFormElements() }` … else `return [.row(_FormRow(.plain(AnyView(view))))]` (:205). **50. `Group`**

- *SwiftUI:* swiftui-docs/Group.md: "Use a group to collect multiple views into a single instance, without affecting the layout of those views"; and explicitly "The modifier applies to all members of the group --- and not to the group itself."

A modified Group therefore lands in the fallback as one opaque child, and its inner TupleView renders through `FrameBuffer(verticallyStacking:)` (TupleViews.swift:50-52) — a hard-coded zero-spacing vertical stack, whatever the parent was. — `Sources/TUIkitView/Rendering/ChildInfo.swift:709`

If the cost is judged too high, record it in SwiftUI-compatibility.md — a Group that silently stops being a group is the class of surprise rule 2 exists to prevent.

**56. `View.onAppear(perform:) / View.task(priority:_:) / View.onDisappear(perform:)`**

- *Status:* **FIXED**: all three key on `context.identity.child(type: Self.self)` — a place per modifier INSTANCE, one step below the identity they render content at — so chaining any of them nests the generic type and the tokens differ. Not the per-identity ordinal this recommended: that counter resets per walk, so a caller that renders without `StateStorage.beginRenderPass()` churns the token, which re-fires an action or restarts a task rather than merely mis-slotting a value.
- *SwiftUI:* swiftui-docs/View.md: onAppear(perform:) — "Adds an action to perform before this view appears… the `action` closure completes before the first rendered frame appears." task(priority:_:) — "Adds an asynchronous task to perform before this view appears." - *TUIkit:* All three key on a token derived from the render identity path alone — LifecycleModifier.swift:29-31 `"\(prefix)-\(context.identity.path)"` — and Renderable modifiers render content at the SAME identity (no withChildIdentity; Renderable.swift:181-192). TUIContext.swift:116-129 `recordAppear` fires only the first (`if !appearedTokens.contains(token) { … action() ; return shouldFire }` … `return false`), and `registerDisappear` (TUIContext.swift:153-157) is a plain `disappearCallbacks[token] = action`, so the second registration overwrites the first. - *Divergence:* `Text("x").onAppear { a() }.onAppear { b() }` runs only the outer closure; `Text("y").task { await load() }.task { await subscribe() }` starts only one task; `Text("z").onDisappear { saveDraft() }.onDisappear { closeFile() }` runs only the inner registration. SwiftUI runs both in all three cases. The realistic route in is a convenience helper that already attaches one applied to a view whose author also wrote one. LifecycleModifierTests.swift covers a single .task (:59) and distinct *sibling* .tasks (:70) — never a chain.
- *Recommendation:* Fix: give the token a per-identity ordinal from the mechanism that already exists for exactly this problem — StateStorage.nextOnChangeIndex(for:) (StateStorage.swift:255-259), whose own doc says it ensures "chained `.onChange(of:)` modifiers don't collide", and which is already reset per walk by beginSceneRender(). If the behaviour is instead to stand, promote the private doc comment into a documented divergence in SwiftUI-compatibility.md §2, since today it is discoverable only by reading a fileprivate function.

**80. `View.frame(minWidth:idealWidth:maxWidth:minHeight:idealHeight:maxHeight:alignment:) — a finite maximum`** · *adjusted on verification*

- *SwiftUI:* swiftui-docs/View.md, the min/ideal/max frame: "If both constraints are specified in a dimension, the frame unconditionally adopts the size proposed for it, clamped to the constraints." and "If a maximum constraint is specified and the size proposed for the frame by the parent is greater than the size of this view, the proposed size, clamped to that maximum." - *TUIkit:* Two problems. (a) `maxWidth: FrameDimension?` (View+Layout.swift:281) and `FrameDimension` is `case fixed(Int) | case infinity` with no ExpressibleByIntegerLiteral conformance anywhere in Sources/, so `.frame(maxWidth: 600)` is a type error. (b) In TUIkit's own spelling the maximum only caps what the content is offered — `contentTargetWidth` returns `min(value, availableWidth)` — and the only branch that GROWS the frame toward a constraint is `if let maximumWidth = maxWidth, case .infinity = maximumWidth { finalWidth = max(finalWidth, context.availableWidth) }`. — `Sources/TUIkit/Modifiers/FrameModifier.swift:78-91 and :156-161 (measure twin at :400-405); declaration at Sources/TUIkit/Extensions/View+Layout.swift:278-293`
- *Divergence:* Executed at 80 columns: `Text("Short").frame(maxWidth: .fixed(30))` renders width 5 (SwiftUI: 30); `Text("Short").frame(minWidth: 10, maxWidth: .fixed(30))` renders width 10 (SwiftUI: 30, since both constraints specified means adopt the proposal clamped). A width-flexible child does reach the cap: `Text("x").frame(maxWidth: .infinity).frame(maxWidth: .fixed(30))` renders 30. So the divergence bites exactly when the child is rigid — the case the modifier exists for. Tests/TUIkitTests/FrameModifierTests.swift:42-58 pins it, commenting "no maxWidth expansion without infinity".
- *Verifier's correction:* Severity should be `silent-divergence`, not `compile-break`. The compile break is the SAFE half — rule 2 is satisfied and the porter is told. The defect that costs a debugging session is underneath it: the obvious mechanical port `maxWidth: 600` to `maxWidth: .fixed(600)` compiles and then does not fill toward the cap. Executed at 80 columns, `Text("Short").frame(maxWidth: .fixed(30))` is 5 wide and `.frame(minWidth: 10, maxWidth: .fixed(30))` is 10 wide, where SwiftUI gives 30 in both cases (View.md:13789-13798: 'If both constraints are specified in a dimension, the frame unconditionally adopts the size proposed for it, clamped to the constraints'). The compile break for `600` is a secondary `missing` spelling. Neither half appears in SwiftUI-compatibility.md; FrameModifierTests.swift:42-58 pins the current behaviour deliberately.
- *Recommendation:* Decide and record. Either make the finite-max branch fill toward its cap the way .infinity does and add ExpressibleByIntegerLiteral to FrameDimension so `.frame(maxWidth: 600)` compiles; or keep the compile break (rule 2 is satisfied) but add a §2 entry, because the obvious mechanical port `600` → `.fixed(600)` silently changes the layout. SwiftUI-compatibility.md says nothing about either half today.

## Method notes, for whoever runs this next

- **Extract Apple's docs locally.** `swift-symbolgraph-extract` over `SwiftUI`
  and `SwiftUICore` carries `docComment` for 93% of declarations. It is faster,
  complete, offline, and pinned to the SDK you actually build against —
  strictly better than fetching developer.apple.com, and it is what let sixteen
  agents work in parallel without a rate limit between them.
- **Availability is per-platform.** See above; both tools that filtered it got
  it wrong the same way.
- **Make the verifier measure, not re-read.** The verifiers that built a probe
  package and printed real buffers produced the corrections; the ones that
  re-read code mostly agreed with the analyst. Linking the repo by path from a
  scratchpad package keeps the working tree clean.
- **A test that skips is not a test that passes.** The first `SecureField`
  clipboard test asserted against the live pasteboard, and passed with the
  guard removed: another suite's clipboard test had clobbered the sentinel, so
  the `guard … else { return }` meant to skip an unavailable helper skipped the
  assertion instead — silently, and green. Inject the dependency.
- **Mutate every fix.** Two of the eleven fixes above had a test that passed
  without them on the first draft.
