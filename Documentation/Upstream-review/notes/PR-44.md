# PR #44 — `codex/ready-foundation`

Commits 1–23 · 2026-07-19 · merged as `6b752fd8` · ~49,000 insertions

Upstream's first post-fork push, and by far its largest. Three unrelated things
in one branch: a CI/quality-gate apparatus, an API-compatibility engine, and the
replacement of the C `stb_image` decoder with vendored pure-Swift codecs.

## Decision

Mostly **not for us** — but not for one reason, so the ledger records four
different verdicts across the branch rather than one.

### The API compatibility engine — `reject`

`4ebe6c06`, `370f5143`, `9f306607` (~8,700 lines). Extracts SwiftUI symbol
graphs across five Apple platforms, canonicalizes them to JSON, and gates CI on
a human-authored `review-policy.json` against a generated
`compatibility-manifest.json` — 12.7 MB, 345,000 lines, checked in.

Genuinely thorough, and genuinely theirs: the policy encodes their API and their
issue numbers, the committed manifest violates our no-large-artifacts norm, and
it needs a pinned Xcode runner and a 6.0.3 toolchain that fights our 6.2.

Our answer to the same problem is `Documentation/SwiftUI-compatibility.md` — a
human narrative, measured against the real SDK when it was written. Assessed at
length on 2026-07-19; the three cheap ideas worth stealing from it (an API
lockfile over OUR public surface, compile-contract fixtures for the parity
claims, a lint for entries whose symbols have vanished) remain unbuilt and
unblocked.

### The pure-Swift image decoder — `reject`

`b8810f10` (vendors swift-png, 27,000 lines), `b6aea725` (deletes
`Sources/CSTBImage`, adds PNG/JPEG decoders and `ImageDecodingLimits`).

The owner ruled on this on 2026-07-19: a pure-Swift decoder is a future
*separate package*, not core TUIkit. We keep `NSImage` where AppKit exists and
`stb_image` elsewhere — see [[nsimage-decoder-selection]]. Nothing here changes
that.

### Bounded image URL loading — `adapt`

`f8655103` is the one commit in this branch with a defect we shared, and it
carries two fixes:

1. **Cached images are not revalidated against the caller's pixel limit.** Real
   here too, and now fixed — `25635228`. The cache is keyed by URL and shared
   process-wide; `maxPixelCount` comes from the environment and varies per view;
   so the first load decided for everyone. Needed an isolated cache to test
   against, which needed `URLImageCache` to be constructible at all — `24bbba32`.
2. **The download is not capped at an encoded byte limit.** Also real here: we
   buffer the entire response before any limit is consulted. Upstream's version
   is a `URLSessionDataDelegate` around a `DispatchSemaphore`, and ours is
   deliberately `async` and cancellable (two tests in `URLImageDownloadTests`
   exist to keep it that way), so it could not have been taken as written.

   **Declined by the owner, 2026-08-06.** The exposure needs an untrusted or
   broken URL that the app itself chose, and closing it would mean new API — a
   byte limit alongside `imageMaxPixelCount` — for that. Not worth it. Recorded
   here rather than left implicit so the next reader does not re-derive the
   same finding and re-open it.

### Deliberately not — `reject`

`0916a406` gates the performance suites behind `TUIKIT_RUN_PERFORMANCE_TESTS`.
Ours cost nothing worth avoiding — the whole suite is 3,680 tests in ~17 s — and
a benchmark that only runs when someone remembers to ask is a benchmark that
stops catching regressions. Keep them in the default path.
