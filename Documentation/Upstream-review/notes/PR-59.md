# PR #59 — `issue/55-render-phase-foundation`

Commits 130–134 · 2026-07-21 · merged as `ab58e228`
(commit 135 is an unrelated badge bump)

The first of four planned slices: replace the boolean `isMeasuring` with a
`RenderPhase` enum, characterise three effect leaks caused by walking the scene
more than once per frame, and fix the one that does not need the later slices.

## Decision

One `adapt` that found a real bug here, one `inspired`, one `reject`, one `n-a`.

## `0cbeb9a0` / `834e65fa` — the leaks · `adapt` (`cdea2eec`)

Upstream characterised three, all from the same root: a frame may walk the
scene more than once inside one `beginRenderPass()`/`endRenderPass()` bracket,
and only the last walk's buffer is drawn.

| Leak | Us |
|---|---|
| duplicate key-handler registration | already fixed — the per-frame registries reset per **walk**, pinned by `RenderPassScopeTests` |
| `onChange(initial:)` double-firing | same fix, same suite |
| `onAppear` fires / `.task` mounts in a discarded walk | **still ours** — now fixed |

The third was live. `RenderLoop.renderContent` builds the first-frame
header-measurement context without setting `isMeasuring`, so every guard written
`!context.isMeasuring` — `onAppear`, `.task`, focus and mouse registration —
treated a walk whose buffer is thrown away as a real render.

Counting fires cannot see it: `recordAppear` is idempotent, so `onAppear` still
fires exactly once. What is wrong is *which* walk it fires in — and that matters
because the two walks see different heights (the first has not subtracted the
header yet), so a tree branching on available space can hold a view in walk one
and not in walk two. That view appears, mounts a task, and is then told it
disappeared, having never been drawn.

Fixed by marking the walk. Safe for the same reason upstream records: our
`AppHeaderModifier` is deliberately **not** guarded on the measure phase, which
is what lets the walk still do its one job — noted at the call site, because
anything that later guards itself that way must stay out of the header's height.

The test asserts the *contract*, not a walk count — every walk before the last
is a measurement, and `onAppear` fires only once the last has begun. Two-pass
layout walks a leaf more than once per walk of the scene, so pinning that number
would fail on any layout change without a defect. Before the fix the probe saw
`[true, false, true, false]` with `onAppear` at walk 2 of 4; after,
`[true, true, true, false]` at 4 of 4.

`834e65fa` also adds `KeyEventDispatcher.handlerCount` "for tests and
diagnostics" — we already have it, added for the registration fix.

## `09bf0e54` — `isMeasuring` → `RenderPhase` · `reject`

A two-case enum in place of the boolean, across 15 sites. Ours has the same 15
sites and the same rule, spelled `!context.isMeasuring`.

Not taken, because the enum's value is entirely in what upstream plans to add to
it later (their PRs #60–#62: pass collectors, pending diff). Today it is a
rename with a wider blast radius than the thing it renames, and the phase name
appears in a dozen doc comments that would all need rewording for no change in
behaviour. Worth revisiting **if** a third phase ever earns its place — at which
point the boolean genuinely stops being able to express it.
