# PR #52 — `issue/10-stable-structural-identity`

Commits 70–80 · 2026-07-20 · merged as `94a0de75`

Runtime records — `@State`, lifecycle slots, `.task` mounts, `@Observable`
registrations — keyed by *structural* identity instead of allocation-time
tokens or sibling position, and kept alive across render-cache hits.

## Decision

**Almost entirely `have`.** This is the branch where upstream arrives at the
identity model this fork already runs on, and the doc comments here say so in
our own words because we hit the same bugs first. Eight of eleven commits record
as `have`; one `defer`, one `queued`, one merge.

That is worth stating plainly rather than as a shrug: the two trees converged on
the same answers independently, which is the strongest evidence available that
the answers are right.

### The four fixes, matched one for one

| Upstream | Ours |
|---|---|
| `1f75c4c8` position-independent keyed child identities | `ViewIdentity.child(erasedType:key:)` — `ForEach` rows key on the element's `id`. The doc comment records why: *"Positional identity handed every row its neighbour's state on reorder."* |
| `d0fdf0f2` lifecycle/task slots from structural paths | `LifecycleModifier` derives every `onAppear`/`.task` token from `context.identity.path`, with the same reasoning written above it: a `UUID()` baked in at construction is fresh on every frame, so the effect re-fires forever. |
| `d1027d27` bind `@State` at committed view identities | `bindStateProperties(of:identity:storage:)` in `Renderable.swift`, called immediately before `body` — *"not the scope it was constructed in, so views swapped by a conditional don't alias each other's state."* See [[state-construction-scope-collision]]. |
| `24039100` preserve `@State` below cache hits | `EquatableView.markSubtreeActive` — `markActive` **plus** `retainSubtree`, on the cache-hit path, so descendant boxes are not garbage-collected while their bodies are skipped. |

`f26d7c1d`'s three assertions all have counterparts in
`LifecycleModifierTests`: *"a .task that mutates @State updates the rendered
output"*, *"a single .task fires exactly once across many frames"*, and the
onDisappear pair (does not fire while present / fires once on removal).

`12390d3f` (observation across cache hits) does not apply for a structural
reason worth recording: their invalidation is scoped to the observed subtree, so
a cached ancestor could strand a registration. Ours calls
`AppState.setNeedsRenderWithCacheClear()`, and `RenderLoop` consumes that flag
into a **full** `clearAll()` — every armed body is re-evaluated and re-armed, so
there is no cache hit to strand anything behind. Coarser, and correct.

`9579f57c` (isolate `@State` locations by runtime) is `n-a` for the reason in
`PR-45.md`: one `AppState.shared`, so there is no second runtime to collide with.

## `d656c1cf` — scoped observation invalidation · `defer`

The other half of that trade. Every `@Observable` mutation currently throws away
the entire render cache, including subtrees that observe nothing. Upstream's
`ObservationRegistry` (115 lines) tracks which identity read which object and
invalidates only that subtree.

Deferred rather than taken because the case for it is a **performance** case and
we do not have the measurement: an app driven by `@Observable` models would pay
a full clear per mutation, but no profile in `Tools/Profiling/` shows that
happening. Build it when a trace says the clears are hot — not before. The shape
to copy is upstream's; the registry is the easy part.

## `a0e4c389` — TaskLocal render hydration · `queued`

Upstream replaced an ambient mutable global, saved and restored around body
evaluation, with a `@TaskLocal`. **Ours is that exact shape**:

```swift
nonisolated(unsafe) public static var activeEnvironment: EnvironmentValues?
```

Production is single-threaded on the render loop, so no production hazard is
demonstrated. The **tests** are another matter: `EnvironmentPropertyTests` and
`ObservableEnvironmentTests` both assign this process-wide global directly (they
have to — they exercise the fallback path that only reads it), neither is
`.serialized`, and swift-testing runs suites in parallel. Any concurrently
running render test entering `withHydration` saves the other suite's value and
restores it over the top. That is precisely the class already fixed twice here —
[[render-cache-test-isolation]] and the StepperOverflow colour-depth flake.

Empirically it has not bitten: 15 consecutive full-suite runs, all green. The
window is a few instructions wide. It is latent, not active.

Not taken unilaterally because `StateRegistration.activeEnvironment` is
`public`, and `@TaskLocal` makes it settable only inside `withValue` — a public
API change plus ~20 test call sites. Queued with a recommendation; see
`open-questions.md`.
