A shared POSIX subprocess runner replacing Foundation `Process` inside the
API-compatibility tool, plus one unrelated test-synchronisation fix.

## Decision

**`n-a`.** Three of the four commits touch nothing but
`Tools/APICompatibility/`, which `PR-44.md` rejected wholesale — there is no
shared surface, so there is nothing to share a defect in. The fourth is a test.

The *class* of bug behind this branch is real and we have already been bitten by
it: a child process whose output exceeds the pipe buffer deadlocks if the parent
waits for exit before draining. That was found in our clipboard paste and fixed
2026-07-20 as `1d6bbad0`; the sweep for remaining instances is recorded in
`PR-47.md` under `03c1bcb0`. Nothing new to do here.

## `98336b5a` — the test commit, and a check it prompted

Upstream replaced a `waitForRequest` helper that polled on a scheduler-dependent
loop with a buffered `AsyncSignal`, and bounded the test with
`.timeLimit(.minutes(1))`. The test itself is `n-a` — it covers per-runtime image
loaders and caches, the architecture we deferred in `PR-45.md`.

The technique was worth a look anyway, because a scheduler-dependent wait is a
flake that only shows up on a loaded CI runner. Ours are a different shape: seven
test files use `Task.sleep`, and every one is a **fixed-duration** wait with a
generous margin (15–250 ms for work that takes microseconds), not a bounded poll
that can run out of iterations. A fixed sleep degrades to *slow*; a bounded poll
degrades to *failing*.

Checked rather than assumed: those suites — `LifecycleManager*`,
`LifecycleModifier`, `StdinArrivalNotifier`, `ClientCapabilityRefresher`,
`SpinnerRowAnimation`, `StateLifecycleRerender`, `URLImageDownload` — were run
five times at 3× core oversubscription (24 spinners on 8 cores). No failures. No
change made.

Worth keeping in mind if that ever stops being true: the fix is an async signal,
not a longer sleep. See [[interaction-test-discipline]].
