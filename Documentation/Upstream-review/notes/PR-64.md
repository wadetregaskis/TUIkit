# PR #64 — `issue/14-cache-effect-loss`

Commits 159–165 · 2026-07-22

Three ways a memoised subtree can serve something wrong, all in the
`EquatableView` / `RenderCache` seam. This is the closest upstream has come to
our own code so far, and the one PR in the review where I have **stopped short
of a verdict on purpose**.

## Decision

One `have`, **two `queued` pending investigation**, and the characterization
test queued with them.

Recording an honest "not yet checked" rather than guessing: each of the two is a
plausible live defect in our tree, each needs a real repro to confirm, and a
wrong `have` here would close a door on something that serves stale pixels.

## `3b6f99d4` — effect-bearing content must bypass the cache · `have`

A subtree carrying `onAppear` / `.task` / a key handler must not be served from
cache, or its effects stop being registered on the frames the cache answers.

Ours declines by a different route and it already covers this:
`LifecycleModifier` calls `volatileReadTracker?.recordRenderSideEffect()` at all
three of its registration sites, and `EquatableView` refuses to **store** a
buffer whose render tripped the tracker (alongside hit-test regions, overlays,
and a mid-render state write). Upstream reaches the same place by snapshotting a
per-pass effect-registration probe; the mechanism differs, the contract holds.

## `e84738728c` — nested entries alive across an outer hit · `queued`

Upstream adds `RenderCache.markSubtreeActive`, keeping every entry *at or below*
a cached subtree root active without traversing it, because an outer cache hit
never walks the inner views that would otherwise mark themselves.

**Ours does this for `StateStorage` and, as far as I can see, not for the cache
itself.** `EquatableView.markSubtreeActive` calls `storage.markActive` +
`storage.retainSubtree`; the cache-hit path calls only `cache.markActive(identity)`
— the root. `RenderCache` has no `markSubtreeActive`.

If that reading is right, nested cache entries below a cached root are
collectable while still live, and the symptom is a cache miss storm rather than
wrong pixels — bad but benign. **Unverified.** What would settle it: a nested
`.equatable()` inside an outer `.equatable()`, render enough frames for a GC
sweep, and assert the inner entry survives.

## `c48e35d7` — style environment in the cache key · `queued`

Their `EnvironmentFingerprint` joins identity, view value and size in the key, so
a style change *above* an `.equatable()` boundary cannot serve a stale buffer.
The members they fingerprint are `foregroundStyle` and `focusIndicatorColor`.

**Our key has no environment component at all.** Global palette/appearance
changes are covered — `RenderLoop.invalidateCacheIfEnvironmentChanged` clears
everything — but a *scoped* style change, e.g. `.foregroundStyle` applied to a
subtree containing an `.equatable()` view whose own value did not change, has
nothing to miss on.

This one would serve **wrong pixels**, not just extra work, so it matters more
than the other. **Unverified.** What would settle it: render an `.equatable()`
subtree under one `.foregroundStyle`, re-render under another with the view
value unchanged, and compare buffers.

## Why this stopped here

Both remaining items need a written repro before a fix, and the session that
reached them had no room left to do that properly. Guessing `have` would be
worse than the honest gap: `PR-45.md` already records what happens when a probe
agrees with its author by accident.

Next session: write the two repros first, then decide. If either reproduces, the
fix shape is upstream's and the design work is done.
