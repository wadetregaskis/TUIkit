# PR #53 — `issue/11-terminal-cell-surface`

Commits 91–108 · 2026-07-20 · merged as `c514d835`
(commit 109 is an unrelated badge bump)

The branch flagged in [[upstream-2026-07-19-deep-dive]] as highest interest:
`FrameBuffer` stops being an array of strings and becomes a grid of terminal
cells, so clipping, compositing and alignment happen in cell space instead of
by re-parsing ANSI out of strings. Everything downstream of that then has to be
refitted, which is what the middle of the branch is.

## Decision

Split three ways.

- **The text-parsing hardening (`2fc51b7c`) — `inspired`.** It found a real
  defect here, now fixed: `edea634a`.
- **The cell surface itself (`3e0db22c`, `cd52b8a5`, and the six refits that
  follow) — `queued`.** The largest architectural divergence in the review so
  far, and not a call to make unilaterally. Recommendation and evidence in
  `open-questions.md`.
- **Everything else — `have` or `n-a`.** Checked individually below.

## `2fc51b7c` — harden terminal text parsing · `inspired`

Upstream's commit "neutralize unsupported CSI, OSC, DCS, and control input"
prompted probing our own equivalent. `sanitizedForTerminal` — the API whose
documented job is *"prevent terminal escape sequence injection"* — was an alias
for `stripped`, which recognises **CSI and nothing else**. Measured, not
assumed:

| input | came out as |
|---|---|
| `ESC ] 52 ; c ; aGVsbG8= BEL` (clipboard write) | `]52;c;aGVsbG8=` |
| `ESC ] 0 ; title ST` (window title) | `]0;title\` |
| `ESC P q # 0 ; 2 ST` (DCS) | `Pq#0;2\` |
| `ESC c` (RIS — full terminal reset) | `c` |
| `U+009B 31 m` (8-bit CSI) | **untouched**, and counted as 3 cells |

Losing the `ESC` meant the 7-bit payloads could not execute, so this was never a
live injection — the failure was visible junk plus a width count that included
it. The 8-bit C1 spellings did not even lose their introducer.

Fixed in `edea634a` with its own scanner over every ECMA-48 family in both
spellings. `stripped` is deliberately **not** widened: it answers "what does
this paint?" for width arithmetic over output this framework generated, on the
hot path of every measure. A test pins the two apart.

## The cell surface · `queued`

**What it does.** `TerminalCell` is `{ content: .empty | .grapheme(String, width:
Int) | .continuation, style: TerminalStyle, isTransparent: Bool }`;
`TerminalSurface` is `[[TerminalCell]]`. `FrameBuffer` stores one and keeps
`lines` as an adapter with a cached, sanitised encoding. Vertical stacking
becomes append-only over rows; compositing handles transparency and wide
graphemes without reparsing strings.

**Why it is attractive.** The cells-not-characters class is standing and
recurring here — see [[cells-not-characters-class]]. A cell grid makes the
*straddling* half of it structurally impossible: you cannot clip a wide
grapheme in half if the second cell is an explicit `.continuation`.

**Why the recommendation is nonetheless to decline it.** Three reasons, in
increasing order of weight:

1. **It fights a profiling-driven design.** `linesAreUniformWidth` and
   `lineWidths` exist on our `FrameBuffer` precisely because per-line
   `strippedLength` was the dominant cost in deeply-nested bordered layouts —
   the same lines re-measured at every enclosing level, O(depth²). A cell grid
   replaces that cost model wholesale and would need the whole
   `Tools/Profiling/` pass re-run to know what it costs.

2. **Upstream's version does not escape strings either.** It keeps the `lines`
   adapter and *parses strings into cells* at the boundary, so it pays the parse
   **and** the per-cell allocation. That is a different point on the trade-off,
   not a strictly better one.

3. **It does not fix the hard part.** Our bugs in this class have almost all
   been *width arithmetic*: is 〰️ two cells, is a lone Fitzpatrick modifier two,
   does Terminal.app under-advance VS-16. `TerminalCell.grapheme(_, width:)`
   still has to compute that number, from the same `terminalWidth`. The grid
   fixes splitting, which we already handle by padding the shortfall.

A narrower borrow is available if the owner wants the safety without the
rewrite: cell-space **clip and composite primitives** used by the few operations
that actually straddle graphemes, leaving `FrameBuffer` as it is. Listed in
`open-questions.md` as the alternative.

The six refits (`95511b4a` blank cells under foreground styling, `ecbca7ee`
ZStack alignment, `6265690a` text layout, `e77ff766` diff clipping, `635c7ac2`
background painting, `b7580bb2` notification measuring) exist only to repair
what the refactor broke. They carry the same `queued` verdict because they have
no meaning apart from it.

## The rest

- **`f082e2ba` — sanitise multiline text atomically · `have`.** Two halves.
  Consuming control payloads *before* splitting logical lines is what
  `edea634a` does by construction: it scans the whole string, so a sequence
  spanning a `\n` is consumed whole rather than half-leaked into the next line.
  Rejecting CRLF clusters is moot here — `TextWrapping` splits on `\n`, `\r\n`
  and `\r` alike, and `\r\n` is one `Character` in Swift, so it never survives
  into a line.
- **`82715e4b` — reserve wide text-field cursor cells · `have`.**
  `TextFieldContentRenderer` already lays out in cells throughout, with the
  reasoning written in: the cursor "cover[s] a wide character whole", and where
  it replaces the first cell "the remainder of a wide character pads". Wide
  characters straddling either window edge are handled at the scroll window too.
- **`1e878467` (linear grapheme mapping), `c153cd60` (scanner streamlining) ·
  `n-a`** — internal refactors of their own parser and renderer.
- Docs and a normalised-style test: `n-a`. Two merges and a badge: `noise`.
