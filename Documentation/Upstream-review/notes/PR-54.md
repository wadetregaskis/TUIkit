# PR #54 — `issue/12-keyed-dynamic-collections`

Commits 110–128 · 2026-07-20/21 · merged as `884a2e0a`
(commit 129 is an unrelated badge bump)

`ForEach` becomes a dynamic-child provider whose children are identified by
their element's `id` rather than their position, and everything that consumes a
collection — `List` rows, `Table` rows, focus, `.task` mounts — follows.

## Decision

**`have`, all but one.** This is `PR-52.md`'s conclusion applied to collections:
the same identity contract, arrived at here first and for the same reason. One
`defer`, three `n-a` for their own tooling and their own test.

### Keyed identity, end to end

`ForEach.makeChild(for:)` is the single constructor behind both the eager
`childViews` and the lazy `childViewCollection`, so the two cannot drift, and it
keys on `String(describing: element[keyPath: idKeyPath])` through
`ViewIdentity.child(erasedType:key:)`. The comment states the contract and what
it replaced: *"Identity is keyed by the element's ID — NOT its position — so a
row's @State / focus / lifecycle follow the element across reorders, insertions
and removals … Positional identity handed every row its neighbour's state when
the data shifted."*

That covers `e357c1a7` (render dynamic children), `9e140571` (flatten through
tuple layouts), `43f9d049` (propagate through builders), `a0634cc4` (list rows at
keyed identities), `1faa6e6b` (table data keyed by row identity) and `94b532e5`
(focus preserved by item ID) at once.

`8b56ca9a` — "keep keyed runtime effects single-mounted" — is our
measure-side-effect rule: `LifecycleModifier` gates every registration on
`!context.isMeasuring`, at three sites, with the rule named in the comment. See
[[measure-side-effect-bug-class]].

Their test commits (`522c6ac6`, `e35ba463`, and the five `Test:` commits at the
end of the branch) all have counterparts here — keyed lifecycle, focus following
IDs, empty and nested `ForEach`, `Table` selection following IDs, insertion into
a keyed collection.

`f9ba1f20` is a fix to *their own test* — a `.task` closure inheriting
`@MainActor` so `Task.sleep` starved cancellation under CI load. Interesting as
a hazard, and one we have already pinned from the other side: *"A cancelled task
sees its cancellation, even after hopping to the main actor"* in
`LifecycleManagerTests`. `n-a`.

## `cbf2c24f` — duplicate collection IDs · `defer`

The one real gap. Two elements sharing an `id` collapse onto one identity and
alias each other's state — our own doc comment says so, and calls it *"the same
app bug it is in SwiftUI"*. But we say it only in a doc comment: nothing tells
the developer at runtime, and the symptom (two rows sharing one row's state) is
baffling until you know to look. SwiftUI itself logs for this.

Deferred rather than done because it is not a small change, and the awkward part
is not the detection:

- detection is easy — `makeChild` already computes the key, so a per-pass `Set`
  finds a collision for the cost of an insert;
- **delivery is not.** A TUI owns the screen: `print` goes into the alternate
  screen buffer and corrupts the frame. Upstream added a whole
  `RuntimeDiagnostics` service, per-runtime, wired through `ServiceEnvironment`
  and `TUIContext`, precisely so the message has somewhere to go that is not
  stdout.

So it needs a diagnostics channel first — and that is a design decision (a
collector the app can read? stderr, which is not the alternate screen? a
debug-build-only trap?) rather than an afternoon. Worth having; not now.
